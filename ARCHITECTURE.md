# Architecture

This document describes the 0.6.0rc1 architecture. Train Guard is a local-first training reliability toolkit with a
zero-required-dependency core and a generated single-file distribution.
Observation is the default; supervised restart is a separate explicit policy.

## Boundaries

- `src/train_guard/` is the only business-logic source of truth.
- `src/train_guard/cli.py` parses commands and delegates to domain modules.
- `core/` owns configuration, events, exit codes, optional imports, privacy, and safe I/O.
- `adapters/` normalizes framework-specific layouts without controlling training.
- `data/`, `env/`, `eval/`, `report/`, and `run/` implement independent diagnostic capabilities.
  `run/launch.py` composes existing preflight, watcher, supervisor, acceptance, and manifest
  primitives; it does not duplicate their business rules.
- `rules/`, `reliability.py`, `state/`, and `sinks/` form the reliability event pipeline.
- `control.py` and `supervisor/` enforce managed-process capability allowlists, checkpoint
  validation, persistent restart budgets, and direct argv execution without shell strings.
- `frameworks/` contains optional callback/plugin entry points; `dashboard/` is loopback-only.
- CLI, the loopback Web dashboard, and the optional Textual TUI consume one persistent status
  model. Observation is read-only by default; Web control requires a one-time in-memory token,
  local origin, and a supervised process explicitly started with `--enable-control`.
- `scripts/` contains repository and release gates, not runtime behavior.
- `release/train_guard.py` is generated by `scripts/bundle_singlefile.py` and must not be edited.

Optional integrations are imported lazily through `core/optional.py`. The package must remain
usable without PyYAML, Pillow, or psutil; those dependencies are exposed only as extras.

## Data and trust model

Commands inspect caller-selected local files and process metadata. They do not install packages
or send telemetry. The watcher never changes training. `run supervise` may launch and restart
an explicitly supplied argv only when the user enables restart, configures a finite budget, and
a checkpoint passes validation. Reports must redact machine identity, private paths,
credential-like values, and raw examples. Atomic and overwrite-safe writes belong in `core/`.

Reliability events use a versioned `symptom -> evidence -> root cause -> action -> outcome`
contract with stable run/event identifiers. SQLite stores bounded runtime state; JSONL remains
the transparent audit/export format. Watcher lifecycle and training lifecycle are separate.

The privacy source gate enumerates exactly `git ls-files`; ignored and untracked local artifacts
are outside that boundary. Binary tracked files fail unless an exact path and rule exemption with
a reason exists. The candidate `release/` tree has a separate complete-tree manifest and privacy
scan. `MANIFEST.in` separately constrains the sdist, while
`configs/release_manifest.json` fixes every single-file candidate path and SHA256 digest.

## Release flow

The version is declared once as `train_guard.__version__`; packaging reads it dynamically.
CI tests the supported operating systems and Python versions, checks quality and coverage,
builds wheel and source distributions, audits dependencies, regenerates the single file, rejects
drift, and runs smoke and contract gates. Tagged release candidates become GitHub prereleases
with wheel, sdist, single-file, checksums, and SBOM. PyPI publishing is disabled because the
`train-guard` project name there belongs to an unrelated project. The distribution therefore
uses the distinct name `llm-train-guard`, while the import package remains `train_guard` and the
CLI remains `train-guard`.

Deprecated aliases `precheck`, `monitor`, `postcheck`, and `evaluate` are a governance
exception for the 0.6.0 candidate cycle only and are scheduled for removal in 0.6.0 final.
Compatibility must not silently expand beyond that window.

Architecture changes should preserve stable exit codes, schema compatibility, read-only
behavior, deterministic output, and the zero-required-dependency installation.
